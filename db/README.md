# Database

PostgreSQL 18. The schema is a set of versioned **goose** migrations, **sqlc**
generates the Go data layer from those same files, and the application connects
with a **least-privilege role** that cannot change the schema or delete money.

## Layout

```
db/
  migrations/        the schema, as goose migrations (00001–00009 = baseline v1.1, 00010 = customers + payment links)
  queries/           sqlc query sources, generated into internal/store   (task sqlc)
  roles.sql          creates templ_app_migrator + templ_app; run once by a superuser
  init/01-roles.sh   Docker only: runs roles.sql when the data volume is first created
  migrations.go      embeds migrations/ so cmd/migrate is a single binary
  erd.mmd            Mermaid ERD, hand-maintained - update it with schema changes
cmd/migrate/         go run ./cmd/migrate up | down | status | version | reset | create NAME
internal/store/      generated by sqlc - never edit by hand
```

## Roles

| role                 | used by                         | can                                                                 | cannot                                        |
|----------------------|---------------------------------|---------------------------------------------------------------------|-----------------------------------------------|
| `postgres`           | Docker, `task db:psql`          | everything (dev only)                                               | -                                             |
| `templ_app_migrator` | `task db:migrate`, deploy jobs  | own and alter every object, CREATE EXTENSION (trusted), run seeds   | superuser, create roles, bypass RLS           |
| `templ_app`          | the application (`DATABASE_URL`) | DML on tables granted in the migrations, EXECUTE functions          | any DDL, DELETE on financial tables, TRUNCATE, write `ledger_balances`, edit reference data beyond `is_enabled`, reprice a fee schedule (only close it) |

Role-level settings: `templ_app` runs with `statement_timeout = 30s`,
`idle_in_transaction_session_timeout = 60s` and a pinned `search_path`;
`templ_app_migrator` runs with `lock_timeout = 10s` so a migration fails fast
instead of blocking traffic while waiting for a lock.

Passwords come from `.env` (`APP_DB_PASSWORD`, `MIGRATOR_DB_PASSWORD`). Outside
Docker, a DBA runs `roles.sql` once:

```bash
psql -v ON_ERROR_STOP=1 -U postgres -d templ_app -v dbname=templ_app -v app_password='…' -v migrator_password='…' -f db/roles.sql
```

## Day to day

```bash
task db            # start Postgres (creates roles on first start) and apply pending migrations
task db:status     # what is applied
task db:new NAME=add_kyc_documents   # new empty migration in db/migrations
task db:migrate    # apply
task db:rollback   # undo the last one
task sqlc          # regenerate internal/store after changing migrations or queries
task db:grants     # privilege matrix of templ_app - check it after adding a table
task db:reset      # drop the volume; next `task db` starts from zero
```

`cmd/migrate` reads `MIGRATE_DATABASE_URL`; the app reads `DATABASE_URL`. Both
are in `.env.example`. Production URLs must use `sslmode=verify-full`.

## Writing a migration

Every migration file has an `Up` and a `Down` section and is applied inside a
transaction. Functions with `$$` bodies must be wrapped in
`-- +goose StatementBegin` / `-- +goose StatementEnd`.

Checklist for a new table:

1. `id UUID PRIMARY KEY DEFAULT uuidv7()`; `BIGINT GENERATED ALWAYS AS IDENTITY` for append-only logs; `SMALLINT` identity for reference tables.
2. `TIMESTAMPTZ` everywhere; `created_at` / `updated_at` with the `set_updated_at` trigger when rows change.
3. Money in `crypto_amount`; add `CHECK`s for sign and range. Prefer `CHECK` and `UNIQUE` over app-side validation - the database is the last line.
4. Uniqueness that involves a nullable column: `UNIQUE NULLS NOT DISTINCT (...)`.
5. Address, memo or tx-hash columns: add a `BEFORE INSERT OR UPDATE` trigger that calls `assert_valid_address` / `assert_valid_tx_hash`.
6. **Grant** exactly what the app needs, right after the table: `GRANT SELECT, INSERT, UPDATE ON t TO templ_app;`. No grant = invisible to the app. No `DELETE` where money or audit is involved.
7. Append-only table: add `forbid_change` as `BEFORE UPDATE OR DELETE` (row) and `BEFORE TRUNCATE` (statement).
8. Views: `CREATE VIEW … WITH (security_invoker = true)`.
9. `SECURITY DEFINER` functions must `SET search_path = pg_catalog, public`.
10. Write the `Down`, update `erd.mmd`, run `task sqlc`, run `task db:grants`.

Reference data (chains, tokens, providers) is added by a migration with
`ON CONFLICT DO NOTHING`, like `00009_seed_reference_data.sql`.

## What the database enforces on its own

- **Deposit addresses are unique** per network, including when `memo` is `NULL`.
- **Chain formats**: addresses, memos and tx hashes are checked against the regex / `supports_memo` of the network they belong to.
- **Ledger**: a journal's entries must sum to zero at `COMMIT`; journals and entries can never be updated, deleted or truncated; `ledger_balances` is written only by a `SECURITY DEFINER` trigger, the app can only read it; the same business event can only be posted once (`UNIQUE (event_type, reference_type, reference_id)`).
- **Audit log** is append-only. Because rows referencing a user, organisation or API key can never change, those parents cannot be hard-deleted once audited - they are closed / anonymised instead, which is the intended lifecycle.
- **Fees**: percentages are basis points (1 % = 100) in `fee_schedules`, resolved
  (org, asset) → (org) → (asset) → platform default, one open row per scope.
  Three revenue layers per schedule: `deposit_fee_bps` with optional min / max,
  a flat `deposit_network_fee` with a `network_fee_payer`, and `spread_bps` on
  the quoted rate. Fixed / min / max amounts must have exactly one denomination:
  the asset, or `fixed_fee_currency` for asset-wide rows; a pure-percentage row
  needs neither. Schedules cannot end before they start, and the app can only
  close one (`UPDATE (effective_to)`), never reprice it - new prices are a new
  row. Every payment / withdrawal stores the `fee_schedule_id`, the bps applied
  and the amounts kept (`fee_amount`, `spread_amount`, `network_fee_amount`);
  their sum cannot exceed the payment.
- **Customers** carry an email or a merchant `external_id` (or both), each
  unique per organization; `status = 'blocked'` and `blocked_at` are kept in
  step by a `CHECK`. Invoices reference them, so a customer is never deleted.
- **Payment links** have either a fixed `price_amount` or a `min`/`max` range
  for payer-chosen amounts, never both; the slug is a 6–64 character URL token,
  `uses_count` counts confirmed invoices and `invoice_ttl_seconds` is bounded
  to 1 minute … 7 days.
- **Amounts, confirmations, attempts** are range-checked.
- **Webhook endpoints** must be `https://`. Filtering private / link-local targets (SSRF) is the app's job, as is validating invoice `callback_url`.
- **Reference tables** (`networks`, `assets`, `payment_providers`, `provider_*`) are read-only for the app except `is_enabled` (and `priority` on `provider_networks`), so a compromised app cannot repoint RPC endpoints or loosen an address regex.
- **Currencies / country codes** must be upper-case ISO codes; slugs are lower-case.
- Secrets never enter the database in clear: tokens and codes are stored as hashes (`*_hash BYTEA`), OAuth tokens, TOTP seeds and webhook secrets as app-side ciphertext (`*_enc BYTEA`), provider credentials as vault references.

## Operations

**Retention.** `login_attempts` (PII), `events`, `exchange_rates` and
`provider_webhook_events` grow without bound and carry a BRIN index on their
time column. Purge as `templ_app_migrator`, e.g.
`DELETE FROM login_attempts WHERE created_at < now() - interval '90 days'`.
`audit_logs` is immutable by trigger; to enforce a legal retention period,
partition it by month in a future migration and drop old partitions.

**Backups.** Use a base backup plus WAL archiving; `pg_dump` of a ledger is
only consistent inside a single snapshot.

**Connections.** The app should use a `pgxpool` sized well below
`max_connections`; put PgBouncer (transaction mode) in front for many replicas.

## Known trade-offs / next steps

- **Row-level security** is not enabled yet. Every merchant-scoped table has
  `organization_id`, so policies of the form
  `USING (organization_id = current_setting('app.org_id')::uuid)` can be added
  once the app has a tenant-context convention (`SET LOCAL app.org_id` per
  request, a separate role for background workers).
- Encrypted columns carry no key id column; the app must embed the key version
  in the ciphertext envelope to allow rotation.
- Nothing stops `approved_by = requested_by` on withdrawals; enforce four-eyes in
  the app or add a `CHECK` once the approval policy is settled.
- Sequential migration numbers (`goose.SetSequential`) are simple for one team
  working on one branch; switch to timestamps if parallel branches collide.
- `uuidv7()` primary keys embed creation time (millisecond precision); fine for
  internal ids, keep using hashes for anything secret.
